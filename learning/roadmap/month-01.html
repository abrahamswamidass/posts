Foundations & the Language of Data Architecture

Core focus

The map before the territory

Everything in data engineering is a reaction to one tension: the database that's great at recording transactions is terrible at analyzing them, and vice versa. Get this one distinction crisp and half the vocabulary falls into place.

Transactional vs analytical (OLTP vs OLAP)

  • OLTP — Online Transaction Processing. Row-oriented, heavily normalized, optimized for many tiny reads/writes. Your MOMS order system. Think "insert one order, fast."
  • OLAP — Online Analytical Processing. Column-oriented, denormalized, optimized for scanning billions of rows across a few columns. Your BigQuery marts. Think "sum revenue by region across two years."
  • Columnar storage & MPP — why warehouses are fast: they store each column together (so a query touches only the columns it needs) and spread work across many nodes (Massively Parallel Processing).

ETL vs ELT — and why the L moved

Old world: Extract, Transform, then Load — transform on a separate box because storage was expensive. Modern world: Extract, Load, then Transform inside the warehouse, because cloud storage is cheap and warehouse compute is elastic. This one reordering is the philosophical core of the modern data stack — you'll live it in Month 2 with dbt.

Dimensional modeling — the Kimball vocabulary

This is the grammar of analytics, and interviewers lean on it hard. A fact table holds measurements (sales amount, quantity) at a defined grain. Dimension tables hold the descriptive context you filter and group by (customer, product, date). Arrange one fact surrounded by dimensions and you have a star schema; normalize those dimensions into sub-tables and it becomes a snowflake schema.

  • Grain — the single most important word here. It's what one row of the fact table means ("one line item per order"). Declare the grain first, always.
  • Surrogate key — a meaningless integer/hash primary key for a dimension, decoupled from the source system's natural/business key.
  • Conformed dimension — a dimension (like Date) shared identically across multiple fact tables, so metrics line up across the business.
  • Degenerate dimension — a dimension attribute (like an order number) that lives on the fact table itself with no separate dimension table.

Slowly Changing Dimensions (SCD)

When a customer moves city, do you overwrite the old value or keep history? That choice has named types, and knowing them cold signals seniority:

  • Type 0 — never changes (retain original).
  • Type 1 — overwrite; no history kept.
  • Type 2 — add a new row with validity dates / a current flag; full history. The one you'll use most.
  • Type 3 — add a column for "previous value"; limited history.
  • Type 4 / 6 — history tables / hybrid combinations.

Medallion architecture & idempotency

The layering pattern you'll see everywhere: Bronze (raw, as-ingested), Silver (cleaned, conformed, deduplicated), Gold (business-level aggregates and marts). And the property that makes pipelines trustworthy: idempotency — running the same job twice produces the same result, no duplicates, no drift. Every reliable pipeline you build for the next 11 months depends on it.

Hands-on challenge
Build · ~6 hours

Model a pharma supply-chain domain into a star schema

Use a domain you know — hospital medication ordering, close to your InteLogix / MOMS work. No cluster needed; a napkin, a diagram tool, and a local Postgres or even a SQL file are enough.

  1. Pick a business process (e.g. "medication dispensed to a patient"). Write one sentence declaring the grain of your fact table.
  2. Identify the measures (quantity, cost, days-supply) and the dimensions (drug, patient, facility, prescriber, date).
  3. Draw the star schema: one fact table, surrounding dimensions, surrogate keys on each dimension.
  4. Choose an SCD type for the facility dimension and justify it in one line (facilities get renamed/merged — history matters).
  5. Write the CREATE TABLE statements and load 20 fake rows. Then write two analytical queries (revenue by facility by month; top 5 drugs by quantity).
  6. Write a one-page ADR (Architecture Decision Record): the decision, the options considered, the trade-offs, the choice.
Stretch — Redraw the same model as a snowflake schema and write two sentences on when the extra normalization is worth it (rarely) and when it isn't (usually).
Learn it with Claude

Prompts that replace the textbook

Paste these into Claude one at a time. Push back, ask for diagrams, ask "why not the other way." Conversation beats reading.

Build the mental map
You are a principal data architect mentoring a senior software engineer who is strong in Java, microservices, and cloud but wants to formalize data-warehousing fundamentals. Explain the difference between OLTP and OLAP systems. Use a concrete healthcare example. Draw a Mermaid diagram contrasting a row-oriented transactional schema with a column-oriented analytical schema, and explain in plain terms why columnar storage and MPP make analytical queries fast. End with 3 sentences I could say in a design meeting to sound fluent.
Dimensional modeling, visualized
Teach me Kimball dimensional modeling by example. Take the business process "a medication is dispensed to a patient in a hospital." Walk me through: (1) declaring the grain, (2) identifying facts vs dimensions, (3) designing a star schema. Render the star schema as a Mermaid entity-relationship diagram with a fact table and 4–5 dimensions, showing surrogate keys. Then define — in one crisp line each — grain, conformed dimension, degenerate dimension, and surrogate key, as I'd say them to a teammate.
Master SCDs with a worked example
Explain Slowly Changing Dimensions types 0 through 6. For each type, show the actual before/after table rows when a customer named "Abraham" moves from Columbus to Dublin. Use small ASCII tables so I can see exactly what changes. Then give me a decision rule: given a new dimension, how do I choose the SCD type in under 30 seconds? Quiz me with 3 scenarios at the end and wait for my answers before revealing yours.
The medallion + idempotency lens
Explain the medallion architecture (bronze/silver/gold) and how it maps onto ETL vs ELT. Then explain idempotency in data pipelines: what it means, why non-idempotent pipelines cause duplicate-data incidents, and three concrete techniques to make a load idempotent (e.g. merge/upsert on a key, delete-insert by partition, deterministic surrogate keys). Give me a Mermaid flowchart of data moving bronze → silver → gold with the transformation at each hop labeled.
Mock interview — junior-architect screen
Act as a hiring manager screening me for a data engineering role. Ask me 6 rapid-fire conceptual questions covering OLTP/OLAP, ELT, star vs snowflake schema, grain, and SCD types. Ask ONE at a time and wait for my answer. After each, rate it 1–5, correct anything wrong, and tell me the sharper way to phrase it. At the end, give me an overall readiness score and the two terms I should drill before Month 2.
Terminology to own

Say these without hesitating

Grain
What a single fact-table row represents. Declared first, before any modeling.
Fact table
Holds numeric measurements at a defined grain; center of a star schema.
Dimension
Descriptive context (who/what/where/when) you filter and group by.
Star schema
One fact table surrounded by denormalized dimensions. The default analytics model.
Snowflake schema
A star whose dimensions are further normalized into sub-tables.
Surrogate key
A synthetic integer/hash PK for a dimension, independent of source business keys.
Conformed dimension
A dimension shared identically across fact tables so metrics reconcile.
SCD (Type 2)
Slowly Changing Dimension that keeps history by adding versioned rows.
OLTP / OLAP
Transaction-optimized vs analysis-optimized systems.
ELT
Load raw first, transform inside the warehouse. The modern default.
Medallion
Bronze (raw) → Silver (clean) → Gold (business) layering pattern.
Idempotency
Re-running a job yields the same result — no duplicates, no drift.
Done when
  • You can declare the grain of a fact table out loud before touching a keyboard.
  • You've built a working star schema with surrogate keys and loaded sample data.
  • You can explain all six SCD types and pick the right one in under 30 seconds.
  • You wrote a one-page ADR justifying your modeling decisions.
  • You survived Claude's mock architect screen with a readiness score you're proud of.
