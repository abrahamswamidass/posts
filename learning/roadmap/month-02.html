Core focus

The stack behind the SQL

You've been running queries against a cloud warehouse for years. This month you go under the hood: why it's fast, what you're actually paying for, and the transformation layer — dbt — that turns ad-hoc SQL into a version-controlled, tested, documented codebase. This is the difference between someone who uses the warehouse and someone who owns it.

Separation of storage and compute

This is the one architectural shift that defines the entire cloud-warehouse era. In the old on-prem world, storage and compute were welded together in a fixed-size cluster: to store more data you bought more machines, and those machines sat idle between queries. Cloud warehouses cut the weld.

  • One copy of the data, many engines — the data lives in cheap object storage (S3/GCS/Azure Blob), and compute is spun up independently against it. Scale compute up for a heavy load, scale it to zero when idle, without touching the data.
  • Isolated compute clusters — Snowflake calls them virtual warehouses: your finance team's dashboard and your data science team's model training can run on separate compute against the same tables, with zero resource contention.
  • Why it killed the fixed cluster — you no longer over-provision for peak and pay for it at 3am. Compute is elastic and metered; storage is nearly free. Every design decision downstream (ELT, on-demand pricing, autoscaling) flows from this split.

The big three, compared

You'll be asked which you'd pick and why. Know the architecture, not just the logo.

  • Snowflake — storage and compute fully separated. Compute is virtual warehouses (T-shirt-sized, per-second billing in credits); data is stored as immutable micro-partitions (~50–500MB compressed, columnar) with metadata that enables aggressive pruning. Auto-clustering keeps hot columns co-located. Pick it for a clean, low-ops SQL warehouse with strong multi-cloud portability.
  • BigQuery — fully serverless: no cluster to size at all. Compute is measured in slots (units of parallelism); you pay either on-demand (per TB scanned) or flat-rate / capacity (reserved slots). Storage is columnar Capacitor format; you tune performance with partitioning (usually by date) and clustering. Pick it when you're already on GCP and want zero infrastructure — which is exactly your Cardinal Health footprint.
  • Databricks — the lakehouse: warehouse semantics on top of a data lake. Data lives in open Delta Lake tables (Parquet + a transaction log giving ACID); Photon is the vectorized C++ query engine; you work in notebooks or SQL warehouses. Pick it when the same platform must serve SQL analytics and Spark/ML on unstructured data.

How the warehouse makes queries fast

The performance tricks are the same handful everywhere, under different names. Internalize them and query tuning stops being guesswork.

  • Columnar storage — each column is stored contiguously and compressed, so a query reads only the columns it touches. This is why SELECT * is a tax and selecting three columns is nearly free.
  • MPP — Massively Parallel Processing splits the scan across many workers (slots / warehouse nodes) that work in parallel and combine results.
  • Partition pruning — if a table is partitioned by date and you filter WHERE dt = '2026-07-01', the engine skips every other partition entirely. The single biggest cost lever you control.
  • Clustering / sort keys — within partitions, co-locating rows by a high-cardinality filter column lets the engine skip blocks (micro-partitions) that can't match your predicate.
  • Predicate pushdown — filters get evaluated as early as possible, at the storage-read layer, so fewer bytes ever reach the compute engine.
  • Result caching — an identical query against unchanged data returns instantly from cache and often costs nothing. Reading a query plan (the EXPLAIN output) tells you which of these actually fired: look for the bytes/partitions scanned and whether a full scan sneaked in.

dbt — analytics engineering

dbt is the T in ELT, done right: transformations written as version-controlled SQL SELECT statements, with tests, docs, and dependency management on top. It's the tool that turns a folder of fragile SQL scripts into software.

  • Models, sources, ref() — a model is a .sql file that's one SELECT; dbt handles the DDL to materialize it. Sources declare your raw tables. ref('other_model') wires models together and auto-builds the dependency (DAG) graph and correct run order.
  • Layered models — the medallion pattern from Month 1 in practice: staging (one model per source, light cleaning/renaming = silver) → intermediate (joins and business logic) → marts (fact + dimension tables the business queries = gold).
  • Tests — declarative data assertions: unique, not_null, relationships (referential integrity), accepted_values. They fail the build when data drifts, which is how you catch a broken upstream feed before a dashboard lies.
  • Docs & lineage — dbt docs generates a searchable site with a column-level lineage graph rendered straight from your ref() calls. This is your self-documenting architecture.
  • Materializations — how a model lands in the warehouse: view (no storage, recomputed on read), table (full rebuild each run), incremental (only process new/changed rows), ephemeral (inlined as a CTE, never materialized).
  • Incremental models — for large fact tables you don't rebuild from scratch. You define a unique_key and dbt does an idempotent merge: new rows insert, matched rows update, so re-running the same window never duplicates.
  • Jinja & macros — dbt SQL is templated. Jinja gives you variables, loops, and conditionals; macros are reusable SQL functions (DRY your CASE logic once, call it everywhere).
  • Seeds & snapshots — seeds are small CSVs version-controlled and loaded as tables (lookup/mapping data). Snapshots implement SCD Type 2 for you: point dbt at a mutable source and it maintains valid_from/valid_to history rows automatically.

Cost is an engineering concern

On a serverless or credit-metered warehouse, a careless query is a line item. Treating spend as a first-class design constraint is a seniority signal — and a preview of the FinOps discipline you'll meet later.

  • Know the economics — BigQuery on-demand charges per TB scanned, not returned; Snowflake bills per second of warehouse uptime by size. The optimization target differs: scan fewer bytes vs. finish faster on a smaller warehouse.
  • Partition to cut bytes scanned — a date-partitioned table with a date filter can turn a 2TB scan into a 5GB one. Same result, 1/400th the bill.
  • Never SELECT * in production — columnar storage means every extra column is bytes scanned you paid for and didn't use.
  • Cluster for pruning — cluster on the columns you filter by most so the engine skips blocks.
  • Choose materializations deliberately — a table that's queried 500×/day should be materialized as a table, not recomputed as a view; a huge fact table should be incremental, not fully rebuilt nightly.
  • Monitor spend — INFORMATION_SCHEMA / query history tells you your most expensive queries. Attribute cost, set budgets, alert on runaway scans. This is FinOps in miniature.
Hands-on challenge
Build · ~7 hours

Build a tested, documented dbt project bronze → silver → gold

Use a free tier — BigQuery sandbox, a Snowflake trial, or Databricks Community Edition. Pick a public dataset you don't mind reasoning about; a retail/orders dataset is ideal because it maps cleanly onto facts and dimensions.

  1. Load a raw public dataset (e.g. a retail/orders set) as your bronze/source and declare it in a dbt sources block.
  2. Build staging models (cleaning, renaming, casting, one per source) — this is your silver layer.
  3. Build a marts model: a star schema with a fact table plus its dimensions — your gold layer.
  4. Add dbt tests (unique, not_null, relationships from fact to dims) and run dbt docs generate to produce the lineage graph.
  5. Convert one model to incremental with a proper unique_key merge. Write two sentences explaining why it's idempotent — re-running the same load can't create duplicates.
  6. Inspect the bytes scanned / cost of one query, then reduce it via partitioning or clustering. Record the before/after numbers.
Stretch — Add a dbt snapshot to implement SCD Type 2 on a dimension (say, customer address). Change a source row, re-run, and note exactly how dbt closes the old row (valid_to) and opens a new one.
Learn it with Claude

Prompts that replace the textbook

Paste these into Claude one at a time. Push back, ask for diagrams, ask "why not the other way." Conversation beats reading.

The shift that made the cloud warehouse
You are a principal data platform architect mentoring a senior software engineer fluent in Java, Airflow, and BigQuery who wants to formalize cloud-warehouse internals. Explain the separation of storage and compute: what it means, why it replaced the old fixed-size cluster, and how it enables isolated compute (e.g. Snowflake virtual warehouses) over one copy of data. Draw a Mermaid diagram showing shared object storage with multiple independent compute clusters. Ground it in a healthcare example — a hospital finance dashboard and a data-science team hitting the same tables without contention. End with 3 sentences I could say in a design meeting to sound fluent.
Snowflake vs BigQuery vs Databricks
Compare Snowflake, BigQuery, and Databricks as a decision table. Rows: architecture, storage format, unit of compute (virtual warehouse / slot / cluster), pricing model, how you tune performance (micro-partitions & auto-clustering vs partitioning & clustering vs Delta/Photon), and best-fit workload. Then give me a "when to pick" paragraph for each — the one scenario where it's clearly the right call and the one where it's the wrong tool. Assume I'm on GCP at work, and tell me honestly when I'd still reach for the other two.
dbt materializations, worked
Teach me dbt materializations: view, table, incremental, and ephemeral. For each, explain what dbt actually does in the warehouse, when to use it, and the cost trade-off. Then write a complete worked example of an incremental model for an orders fact table — include the config block, the is_incremental() filter, and a unique_key. Walk me through the generated merge statement line by line and explain precisely why re-running the same batch is idempotent and can't create duplicate rows. Finish by quizzing me: give me 3 models and ask which materialization I'd choose, waiting for my answer each time.
Cut this query's cost
Explain how to reduce the cost of an expensive BigQuery (or Snowflake) query using partitioning, clustering, and pruning. Start with a concrete "before" query that scans a huge unpartitioned events table with a date filter and a SELECT *. Show the DDL to partition and cluster the table, rewrite the query, and give me realistic before/after bytes-scanned and cost numbers. Explain, mechanically, why partition pruning and predicate pushdown make the difference. Then list the 5 cost habits I should apply to every query I write from now on.
Mock interview — analytics engineer
Act as a hiring manager screening me for an analytics engineer role. Ask me 6 rapid-fire questions covering separation of storage & compute, Snowflake vs BigQuery vs Databricks, dbt materializations and incremental models, idempotent merges, partitioning/clustering, and query-cost reduction. Terminology to own

Say these without hesitating

Separation of storage & compute
Data in cheap object storage, compute spun up independently against it — the defining cloud-warehouse shift.
Virtual warehouse
Snowflake's isolated, resizable compute cluster; billed per second in credits.
Slot
BigQuery's unit of compute parallelism; you buy them on-demand or reserved.
Micro-partition
Snowflake's immutable ~50–500MB columnar storage unit with pruning metadata.
Pruning
Skipping partitions/blocks that can't match a query's filter — the core cost lever.
Clustering
Co-locating rows by a filter column so the engine skips non-matching blocks.
Materialization
How dbt lands a model: view, table, incremental, or ephemeral.
Incremental model
A dbt model that processes only new/changed rows instead of a full rebuild.
dbt ref()
Wires models together and auto-builds the dependency DAG and run order.
Idempotent merge
An upsert on a unique key so re-running a load never duplicates rows.
Result cache
An identical query on unchanged data returns instantly and often for free.
MPP
Massively Parallel Processing — splitting a scan across many workers at once.
Done when
  • You have a working dbt project running bronze → silver → gold on a real warehouse.
  • Your models have passing dbt tests and a generated lineage-graph doc site.
  • You built one incremental model and can explain why its merge is idempotent.
  • You reduced a query's bytes-scanned via partitioning/clustering and know exactly why it worked.
  • You can pick Snowflake vs BigQuery vs Databricks for a given scenario and defend the choice.
