Core focus

Machine learning, from an engineer's chair

You've spent a career writing deterministic code: given this input, produce exactly that output, every time. Machine learning inverts the relationship. You hand it inputs and the answers, and it learns the function that connects them. Get that reframing crisp and the rest of the AI phase stops feeling like magic and starts feeling like pipelines you already know how to build.

The engineer's model of ML

In your world, a rule is something you author: if reorder_days < 3 then flag. In ML, you don't write the rule — you give the machine labeled examples and it infers the rule from data. That's the whole shift: deterministic code versus learned behavior. You stop specifying logic and start curating examples.

  • Supervised — you have labeled data (inputs paired with known answers). Predict readmission given a patient record. This is 90% of applied ML and all of your work this month.
  • Unsupervised — no labels; the model finds structure on its own (clustering patients into cohorts, detecting anomalies). Useful when you don't know the answer, only that patterns exist.
  • Reinforcement learning — an agent learns by acting and getting rewarded/penalized. One sentence is enough for now: it's how you train things that make sequences of decisions (game play, robotics, and — later — some LLM alignment).
  • Classification vs regression — two flavors of supervised learning. Classification predicts a category ("will readmit / won't"). Regression predicts a number ("length of stay in days"). Same lifecycle, different output and different metrics.

Features are the whole game

Everyone imagines ML is about picking clever algorithms. In practice, the model is a commodity and the features are where you win or lose. A feature is one input column the model learns from; the label is the answer column you're trying to predict. Turning raw data into good features is exactly the ETL muscle you already have.

  • Feature engineering — encoding categoricals (one-hot, target encoding), scaling numerics so no single column dominates, aggregating (count of prior admissions), and deriving time features (day-of-week, days-since-last-visit). This is SQL and pandas, not calculus.
  • Feature leakage — the deadly bug. Information that wouldn't exist at prediction time sneaks into training, so the model looks brilliant in the notebook and collapses in production. Classic cases: a "discharge_disposition" column that's only filled in after the outcome, or scaling using statistics computed over the full dataset (test rows leak into training). The rule: every feature must be knowable before the moment you'd actually make the prediction. Fit all transforms on the training split only.
  • Feature store — the concept that should feel like home. A central place that serves the same feature definitions to both training (offline, batch, historical) and serving (online, low-latency). The value is offline/online parity: the "days since last visit" your model trained on is computed identically to the one it sees in production. This is a data-engineering problem wearing an ML hat — you're already qualified.

Training without fooling yourself

The core discipline of ML is not letting yourself believe a bad model is good. Almost every mechanism below exists to keep you honest.

  • Train / validation / test split — train on one slice, tune on a second (validation), and touch the third (test) exactly once, at the end, as your unbiased estimate. Look at the test set repeatedly and you've quietly overfit to it.
  • Overfitting vs underfitting — an overfit model memorizes the training data (including its noise) and fails on anything new. An underfit model is too simple to capture the real pattern. You want the middle.
  • Bias-variance tradeoff — the vocabulary for that middle. High bias = too simple = underfit. High variance = too sensitive to the training sample = overfit. Tuning a model is largely trading one for the other.
  • Regularization — a penalty that discourages the model from getting too complex (L1/Lasso, L2/Ridge). It's how you push a high-variance model back toward simplicity on purpose.
  • Cross-validation — instead of one train/validation split, rotate through k folds so every row gets a turn being validation. A more stable read on real performance, especially on smaller datasets.

Here's the punchline that catches beginners: a model scoring 99% accuracy is more often a red flag than a triumph. It usually means leakage, an overfit, or a class imbalance the metric is hiding. Distrust suspiciously good numbers — that instinct is what separates an engineer from a Kaggle tourist.

Evaluation — the vocabulary interviewers probe

Accuracy is the metric everyone reaches for and the one that lies most. Own the alternatives cold, because a screen will push here.

  • Confusion matrix — the 2×2 (true/false × positive/negative) that every classification metric is built from. Read it and you can derive the rest.
  • Precision vs recall — precision asks "of the cases I flagged, how many were real?" Recall asks "of the real cases, how many did I catch?" In healthcare the tradeoff is life-and-death: for a serious-disease screen, a false negative (missing a sick patient) is far costlier than a false positive (a scare and a follow-up test), so you optimize recall. For flagging patients for an expensive, risky intervention, false positives hurt, so you weight precision. The metric follows the cost.
  • F1 — the harmonic mean of precision and recall, for when you need a single number and both matter.
  • ROC-AUC — how well the model separates the classes across all thresholds, independent of where you draw the line. 0.5 is a coin flip; 1.0 is perfect. Great for comparing models; pair it with a threshold-specific metric for the actual decision.
  • Regression metrics — no confusion matrix here. RMSE (penalizes big misses hard), MAE (average absolute error, more robust to outliers), and R² (fraction of variance explained). Pick by whether large errors are disproportionately bad.

The senior move isn't reciting these — it's choosing the metric that matches the business cost of being wrong, and saying so out loud before you train anything.

From notebook to production (MLOps preview)

A model in a notebook is worth nothing. The last mile — serving, tracking, monitoring — is where a data engineer becomes an ML engineer, and it's the mile where your existing skills transfer almost one-for-one.

  • Batch vs online inference — batch scores millions of rows on a schedule (nightly readmission-risk run) and writes results to a table. Online serves a single prediction in milliseconds behind an API. Same model, radically different infrastructure — and you've built both shapes of pipeline before.
  • Model serving as an API — wrap the trained model behind an HTTP endpoint (FastAPI) so any service can call it. This is just microservices, which you already do in your sleep.
  • Experiment tracking — MLflow logs each run's parameters, metrics, and artifacts so you can reproduce and compare instead of guessing which notebook cell produced that number. Version control for experiments.
  • Model registry — the promotion pipeline for models (staging → production → archived), with versions and lineage. The deployment discipline you already apply to services, applied to models.
  • Monitoring for drift — models rot. Data drift is the input distribution shifting (a new hospital sends differently-shaped records). Concept drift is the relationship between input and outcome changing (a new treatment protocol changes what predicts readmission). Both silently degrade a model that looked perfect at launch, and catching them is a monitoring/observability problem — your home turf.
Hands-on challenge
Build · ~8 hours

Train, evaluate, and serve your first real model

End to end: raw table in, live prediction endpoint out. Pick a public tabular dataset you'll actually care about — hospital readmission, customer churn, or similar. Everything runs locally in a notebook plus a small FastAPI app; no GPU, no cloud.

  1. Load the dataset and do feature engineering with pandas: encode categoricals, scale numerics, aggregate, and derive at least one time feature. Write one sentence declaring what you're predicting (the label) and at what moment the prediction would be made.
  2. Train a baseline model with scikit-learn — logistic regression or gradient boosting. Baseline first; fancy later.
  3. Evaluate properly: a clean train/test split, cross-validation, a confusion matrix, precision/recall/F1, and ROC-AUC. Then write two sentences on which metric matters for this use case and why — tie it to the cost of a false negative vs false positive.
  4. Break it on purpose: deliberately introduce a feature-leakage bug (e.g. include a post-outcome column, or fit your scaler on the full dataset before splitting). Watch the score jump to something suspiciously great, then catch it, explain how it leaked, and fix it. This one exercise will save you a production incident someday.
  5. Track the experiment with MLflow: log the parameters, the metrics, and the trained model as an artifact.
  6. Serve it: wrap the trained model in a small FastAPI endpoint that takes a JSON record and returns a prediction. Hit it with curl and get a live score back.
Stretch — Log a second model (different algorithm or hyperparameters), compare the two runs side by side in the MLflow UI, and write 3 sentences on why you'd ship one over the other — including the metric and the business cost that drove the call.

Bias-variance, drawn
Explain the bias-variance tradeoff and overfitting to me visually. Draw an ASCII plot of training error vs validation error as model complexity increases — show the classic gap where training error keeps dropping but validation error turns back up, and mark the underfit, sweet-spot, and overfit zones. Then give me the plain-English intuition for each zone, explain how regularization and cross-validation help, and tell me the one sentence I'd say to explain overfitting to a skeptical manager.
Confusion matrix, healthcare edition
Walk me through a confusion matrix using a healthcare example — say, a model screening patients for a serious condition. Draw the 2×2 as an ASCII table with true/false positive/negative, then derive precision, recall, and F1 from it in plain terms. Explain concretely when precision matters more than recall and vice versa, using the cost of a missed diagnosis vs a false alarm. Then quiz me: give me 3 different scenarios and ask which metric I'd optimize for each. Wait for my answer before revealing yours.
Hunt down feature leakage
Explain feature leakage as if it's the most dangerous bug in applied ML. Give me 3 concrete, realistic examples of how it sneaks into a training pipeline — including one from scaling/preprocessing done wrong and one from a column that's only populated after the outcome is known. For each example, show how it inflates the score and give me the specific technique to prevent it. Finish with a 5-item checklist I can run against any feature set before I trust a model's numbers.

Terminology to own

Say these without hesitating

Feature
An input column the model learns from; the raw material of every prediction.
Label
The answer column you're training the model to predict.
Overfitting
A model that memorizes training data (noise included) and fails on new data.
Bias-variance tradeoff
The tension between too simple (bias/underfit) and too sensitive (variance/overfit).
Regularization
A complexity penalty (L1/L2) that pushes an overfit model back toward simplicity.
Cross-validation
Rotating through k folds so every row validates once — a stable performance read.
Precision
Of the cases you flagged, the fraction that were actually positive.
Recall
Of the actual positives, the fraction you caught.
F1
Harmonic mean of precision and recall — one number when both matter.
ROC-AUC
How well a model separates classes across all thresholds; 0.5 is a coin flip.
Feature store
Central feature definitions serving training and serving identically (offline/online parity).
Model drift
Silent decay as inputs (data drift) or input-outcome relationships (concept drift) shift.
Inference
Making predictions with a trained model — batch (scheduled, bulk) or online (real-time API).
Done when
  • You've trained and properly evaluated a scikit-learn model on a real tabular dataset.
  • You can read a confusion matrix cold and pick precision vs recall for a given use case.
  • You deliberately introduced a feature-leakage bug, caught it, and can explain how it snuck in.
  • You have an MLflow-tracked experiment you can reproduce and compare.
  • You have a working inference API that returns a live prediction from a JSON request.
