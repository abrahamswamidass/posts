Distributed Batch Processing with Spark

When data outgrows a single machine, Spark is the answer the industry reaches for. This month you learn how it actually executes — and the lakehouse table formats that put ACID transactions on the data lake.

Core focus

How Spark actually runs your job

You've run Dataflow and BigQuery; you know what distributed compute feels like from the outside. Spark is where you learn what's happening on the inside — and the mental model transfers to almost every batch engine you'll ever touch. Get the execution model and the shuffle crisp, and Spark stops being magic.

Why distributed compute

A single machine has a ceiling: one box's RAM, cores, and disk. Scale-up (buy a bigger machine) hits diminishing returns and a hard wall fast. Scale-out (add more commodity machines) is effectively unbounded — and that's the bet Spark makes. It's an in-memory distributed engine: it partitions your data across a cluster, keeps working sets in RAM where it can, and coordinates parallel computation over those partitions. It is not a warehouse — it doesn't own your storage or serve low-latency queries. Reach for Spark when you need programmatic transformation over huge datasets (ML feature pipelines, complex joins, semi-structured data); reach for BigQuery when you want SQL analytics over managed columnar storage.

Spark's execution model

Three roles run every job. The driver holds your program, builds the execution plan, and schedules work. The executors are worker processes that actually run tasks on partitions and hold cached data. The cluster manager (YARN, Kubernetes, or Spark standalone) hands out the executors. The driver plans; the executors do; the manager provisions.

  • RDD → DataFrame → Dataset — RDDs were the original low-level, unstructured API. DataFrames added a schema and unlocked the query optimizer; Datasets add compile-time type safety (JVM only). Use DataFrames (or Spark SQL) for nearly everything — you get Catalyst's optimizations for free.
  • Lazy evaluation and the DAG — Spark doesn't execute as you write. Each transformation appends to a DAG (directed acyclic graph) of operations. Only an action triggers the whole plan to run, which lets Catalyst optimize across the entire chain before a single byte moves.
  • Transformations vs actions — transformations (map, filter, join, groupBy) are lazy and return a new DataFrame. Actions (count, collect, write) force execution. Nothing runs until an action — a fact that explains most "why is my code doing nothing / doing everything at once" confusion.

The shuffle — where performance lives or dies

Dependencies come in two flavors. Narrow transformations (map, filter) need only the data already in a partition — no data movement, embarrassingly parallel. Wide transformations (groupBy, join, repartition) need rows from across partitions, which forces a shuffle: Spark writes intermediate data, moves it across the network, and re-partitions by key. The shuffle is the single most expensive thing Spark does — it's disk I/O plus network plus serialization. Everything about performance tuning is really about minimizing and balancing shuffles. Partitioning and partition count govern parallelism; spark.sql.shuffle.partitions (default 200) sets how many partitions a shuffle produces — too few and tasks are huge, too many and you drown in scheduling overhead.

Joins and skew

Two join strategies dominate. A broadcast join ships a small table in full to every executor so the large side never shuffles — by far the cheapest option when one side fits in memory. A sort-merge join shuffles and sorts both sides by the join key, then merges — the workhorse for two large tables. Data skew is the classic killer: one hot key (think a null facility_id or a dominant drug code) lands most rows in a single partition, so 199 tasks finish and one straggler runs for an hour.

  • Salting — append a random suffix to the hot key to spread it across partitions, join on the salted key, then aggregate back.
  • Broadcast — if the other side is small, broadcasting sidesteps the skewed shuffle entirely.
  • AQE (Adaptive Query Execution) — Spark 3+ re-plans mid-flight using runtime statistics: it can coalesce shuffle partitions, switch to a broadcast join, and split skewed partitions automatically. Turn it on and understand what it's doing for you.

Caching / persist keeps a DataFrame in memory (or memory-and-disk) so a reused intermediate isn't recomputed from the DAG on every action — worth it when you branch off the same result multiple times, wasteful when you read it once. Under the hood, the Catalyst optimizer rewrites your logical plan (predicate pushdown, join reordering, constant folding) into an efficient physical plan, and Tungsten makes execution fast with off-heap memory management, cache-aware computation, and whole-stage code generation — together they're why DataFrames beat hand-tuned RDD code.

Lakehouse table formats

Raw Parquet files sitting in object storage give you cheap columnar scans and nothing else: no ACID, no safe concurrent updates, no consistent read while a write is in flight, no way to MERGE or query yesterday's version. Delta Lake, Apache Iceberg, and Apache Hudi all solve this the same way — a transaction log / metadata layer that sits on top of the Parquet files and tracks which files make up each version of the table. That layer buys you ACID transactions, time travel (query a table as of an old version or timestamp), schema evolution (add/rename columns without rewriting), upserts/MERGE, and safe concurrent reads and writes. That combination — warehouse-grade table semantics directly on cheap lake storage — is what earns the name lakehouse.

  • Delta Lake — a JSON/Parquet transaction log; deepest integration with Spark and Databricks; the easiest on-ramp.
  • Apache Iceberg — engine-agnostic table spec with hidden partitioning and strong catalog support; the emerging open standard across Spark, Flink, Trino, and warehouses (including BigQuery).
  • Apache Hudi — built for incremental, upsert-heavy streaming ingestion with copy-on-write and merge-on-read table types.
Hands-on challenge
Build · ~8 hours

A PySpark job end to end — skew fix, Delta table, time travel

Use Databricks Community Edition (free) or a local Spark install. Grab a real open dataset — NYC taxi trips is ideal (big enough to shuffle, has natural join keys and skew). The point isn't the analytics; it's watching Spark execute and touching every concept above with your own hands.

  1. Read the raw data into a DataFrame and inspect the schema and partition count.
  2. Do transformations plus an aggregation — e.g. average fare by pickup hour and zone.
  3. Deliberately create or find a skewed join (join trips to a zone lookup on a hot key), observe the straggler task, then fix it with a broadcast or salting. Note the runtime difference before and after.
  4. Write the output as a Delta (or Iceberg) table.
  5. MERGE to update some rows, then use time travel to query the previous version and diff it against the current one.
  6. Evolve the schema by adding a column, write again, and confirm the old data still reads cleanly.
Stretch — Open the Spark UI for one job. Identify the stages, find the shuffle boundary, and locate the slowest task. Write 3 sentences on what you saw — where the time went and why.

The shuffle, drawn out

Contrast narrow transformations (map, filter) with wide transformations (groupBy, join, repartition), and show with an ASCII or Mermaid diagram how data stays put for narrow ops but moves across partitions and the network for wide ops. Diagnose a skewed join
I have a Spark job where one join is dramatically slower than the rest of the DAG. Explain how data skew shows up as a symptom in the Spark UI (one straggler task, uneven task durations in a stage) and how I'd confirm it's skew. Include a worked salting example in PySpark: show the hot key, the salt column, the salted join, and the aggregate-back step, with code.
Delta vs Iceberg vs Hudi
Compare Delta Lake, Apache Iceberg, and Apache Hudi in a single table with rows for: ACID transactions, time travel, schema evolution, upserts/MERGE, and ecosystem/engine support. Terminology to own

Say these without hesitating

Shuffle
Redistributing data across partitions and the network for a wide op. Spark's most expensive step.
Narrow transformation
Needs only data in the current partition (map, filter). No data movement.
Wide transformation
Needs data from other partitions (groupBy, join). Forces a shuffle.
Broadcast join
Ships a small table to every executor so the large side never shuffles.
Sort-merge join
Shuffles and sorts both sides by key, then merges. The workhorse for two large tables.
Data skew
A hot key overloads one partition, creating a straggler task that stalls the stage.
Partition
A chunk of a distributed dataset processed by one task. Parallelism unit.
Lazy evaluation
Transformations only build a DAG; nothing runs until an action.
Predicate pushdown
Catalyst pushes filters down to the scan so less data is read.
Lakehouse
Warehouse-grade table semantics on cheap lake storage via a metadata layer.
ACID (on the lake)
Transactional guarantees on object storage, provided by Delta/Iceberg/Hudi.
Time travel
Querying a table as of an earlier version or timestamp.
Schema evolution
Changing a table's schema (add/rename columns) without rewriting the data.
Catalyst
Spark's query optimizer; rewrites logical plans into efficient physical ones.
Done when
  • You've written a PySpark job that reads → transforms → aggregates → writes.
  • You fixed a skewed join and can explain the shuffle behind it.
  • You wrote a Delta/Iceberg table, did a MERGE, and used time travel to read a prior version.
  • You can read a Spark UI DAG — stages, shuffle boundary, and the slowest task.
  • You can compare Delta, Iceberg, and Hudi on demand and say when to pick each.
