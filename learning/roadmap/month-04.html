Streaming & Real-Time Data

You ship Kafka microservices already. This month you turn that into a real-time data engineering skill — stream processing, windows, watermarks, exactly-once, and the architectural debate every senior gets asked about.

Core focus

The log is the source of truth

You use Kafka as a message bus between services — fire an event, another service reacts. Real-time data engineering asks a different question: what if the stream itself is the dataset, and you compute aggregates, joins, and marts over it continuously instead of once a night? That reframing — from moving messages to processing an unbounded table — is what this month installs.

Event-driven thinking

Request/response asks "what is the current state?" Event-driven flips it: state is the fold over a stream of immutable events. Nothing is updated in place; you append a new fact ("order-42 shipped") and let readers derive the present from the history. The log becomes the source of truth, and producers and consumers are fully decoupled — a producer doesn't know or care who reads, and you can add a new consumer months later that replays the entire history to build a fresh view. That replayability is the superpower you'll lean on all month.

Kafka, deeper than you use it

You know how to produce and consume. Here's the machinery that matters when you're the one designing the topic:

  • Partitions are the unit of parallelism. A topic is split into partitions; each is an ordered, append-only log. Consumer throughput scales with partition count — you cannot have more active consumers in a group than partitions.
  • Offsets — each message's position within its partition. Consumers commit offsets to record progress; where and when you commit is exactly what determines your delivery semantics (below).
  • Consumer groups & rebalancing — partitions are distributed across members of a group. Add/remove a consumer, or one dies, and Kafka rebalances — reassigns partitions, briefly pausing consumption. Frequent rebalances (from slow processing tripping max.poll.interval) are a classic prod pathology.
  • Ordering is per-partition only. This is the sentence seniors get wrong. Kafka guarantees order within a partition, never across the topic. If two events must be ordered, they must share a partition — which means they must share a key.
  • Keys & partitioning strategy — the key is hashed to pick a partition. Choose a key so that all events needing ordering (e.g. same patient_id) land together, and so load spreads evenly. A skewed key (one hot facility) creates a hot partition and wrecks parallelism.
  • Retention vs log compaction — retention deletes messages older than a time/size bound (a true event stream). Compaction instead keeps the latest value per key forever, deleting superseded ones — turning the topic into a durable changelog you can replay to rebuild state (think: current inventory per SKU).
  • Replication & ISR — each partition has a leader and follower replicas. The in-sync replica (ISR) set is the replicas caught up to the leader; acks=all means a write isn't acknowledged until the ISR set has it. That's the knob balancing durability against latency.

Delivery semantics

Three guarantees, and the whole game is knowing which one your pipeline actually gives:

  • At-most-once — commit the offset before processing. Crash mid-work and the message is lost. Fast, lossy.
  • At-least-once — commit after processing. Crash before the commit and you reprocess on restart — duplicates. This is the common default.
  • Exactly-once — every event affects the result once, despite retries and crashes.

Exactly-once is hard because it demands two things together: dedup (recognize a message you've already handled) and an atomic commit (the side effect and the offset advance succeed or fail as one unit — no window where one happened and the other didn't). Kafka delivers this with the idempotent producer (sequence numbers let the broker drop retried duplicates) plus transactions (write output records and commit consumer offsets in one atomic transaction — "read-process-write"). Map it to real risk: at-least-once on an order pipeline means a broker hiccup can bill a patient's medication order twice. Exactly-once is the difference between "we retry safely" and a 2 a.m. incident about duplicate charges.

Stream processing & windows

Processing splits into stateless (map/filter each event independently — trivial to scale) and stateful (aggregations, joins, dedup — the engine must keep and checkpoint state). Aggregating an unbounded stream forces the question: over what slice of time?

  • Tumbling — fixed, non-overlapping windows (every 5 minutes, back to back). Each event lands in exactly one.
  • Sliding — fixed length that overlaps (a 5-minute window advancing every 1 minute). An event can fall in several; good for moving averages.
  • Session — dynamic, defined by a gap of inactivity (close the window after 30 minutes of silence). Length varies per key.

The decisive distinction is event-time vs processing-time. Processing-time is when your engine saw the event; event-time is when it actually happened (the timestamp in the record). Real streams arrive late and out of order — a mobile scanner buffers offline and flushes an hour later. You almost always want to window by event-time so results are correct and reproducible on replay. But if you window by event-time, how long do you wait for stragglers before you close a window and emit its result? That's the job of a watermark: a moving assertion that "I've probably seen everything up to time T." Data older than the watermark is late; you configure a bound (accept up to 10 minutes late, then drop) to trade completeness against latency and unbounded state. Choose the engine to match: Flink is a true event-at-a-time streaming engine with the lowest latency and the richest windowing/state model; Spark Structured Streaming is micro-batch (tiny batches under a streaming API) — slightly higher latency but one unified engine and mental model for batch and streaming, which is why it wins when you already live in Spark.

CDC and architecture patterns

Change Data Capture turns a database into a stream. Instead of polling a table, Debezium reads the DB's transaction log (Postgres WAL, MySQL binlog) and emits an event for every row insert/update/delete — low-impact, ordered, and complete. It's how you get an OLTP system's changes into Kafka in near-real-time to feed the lakehouse. Each change event carries a before and after image plus operation metadata, so downstream you can rebuild the table's exact state.

Now the debate you'll get asked to whiteboard. Lambda architecture runs two paths: a batch layer that recomputes accurate results over all history, a speed layer that computes approximate real-time results over recent data, and a serving layer that merges them. It's robust but you maintain the same logic twice, in two codebases, and reconciling them is a permanent tax. Kappa architecture deletes the batch layer: there's one streaming path, and when you need to "reprocess" (bug fix, new metric, backfill) you simply replay the log from the beginning through the same code. Kappa is simpler and DRY, and it's viable precisely because Kafka retains/replays. Choose Lambda when batch and streaming genuinely need different logic or your batch corrections must reconcile an approximate speed layer; choose Kappa when one code path can serve both and your retention lets you replay — the modern default for greenfield.

Backpressure — when a downstream consumer can't keep up with an upstream producer. A healthy system propagates the slowdown backward (the source throttles) rather than buffering unboundedly until it OOMs; Kafka absorbs bursts by design (the log is the buffer), while stream engines like Flink signal backpressure through their network stack to slow ingestion. Watch it, because a silently lagging consumer is a stale-data incident waiting to happen.

Hands-on challenge
Build · ~8 hours

Build a windowed streaming pipeline with watermarks

Stand up a real stream and process it. Use local Kafka in Docker (or Redpanda for a lighter single-binary broker) plus Spark Structured Streaming (or Flink if you want the true-streaming model). Keep it in a domain you know — medication scan events flowing off hospital devices.

  1. Produce a stream of synthetic medication scan events — each with an event-time timestamp, a facility_id, and a drug_id — to a Kafka topic, using facility_id as the partition key so a facility's events stay ordered.
  2. Consume the topic with Structured Streaming, parsing the event-time field out of each record.
  3. Compute a windowed aggregation: count of scans per 5-minute tumbling window per facility, with a watermark that drops data arriving more than 10 minutes late.
  4. Deliberately inject a late event — one timestamped well in the past — and observe the watermark behavior: watch it get folded into its window when within the bound, then dropped once you push it past 10 minutes late.
  5. Sink the results to a Delta table (or the console to start) with checkpointing enabled, so the query recovers its offsets and state after a restart.
  6. Write 4 sentences stating the delivery semantics your pipeline actually provides end to end — be honest about where at-least-once vs exactly-once holds, given your source, your checkpointing, and your sink.
Stretch — Add a Debezium CDC connector on a Postgres table and stream inserts/updates into Kafka. Fire a few INSERT/UPDATEs and describe, in a short paragraph, exactly what the change events look like — the before/after payloads, the op field, and how you'd rebuild the table's current state from them.
Learn it with Claude

Prompts that replace the textbook

Paste these into Claude one at a time. Push back, ask for diagrams, ask "why not the other way." Conversation beats reading.

Kafka internals, past the API
You are a principal streaming-platform engineer mentoring a senior software engineer who already ships Kafka microservices but uses Kafka mostly as a message bus. Go deeper: explain topics, partitions, consumer groups, and offsets as the machinery of a distributed log. Render a Mermaid diagram of one topic with 3 partitions and a consumer group of 2 consumers, showing partition assignment. Then explain precisely why ordering is guaranteed per-partition only and never across a topic, and what that forces about my choice of partition key. End with 3 sentences I could say in a design review to sound like I know the internals.
Delivery semantics & the duplicate-order incident
Explain at-most-once, at-least-once, and exactly-once delivery in terms of when the consumer commits its offset relative to doing the work. Then tell me a concrete failure story: a healthcare order pipeline running at-least-once, a broker hiccup and consumer restart, and how it results in a patient's medication order being billed twice. Walk through the fix — Kafka's idempotent producer plus transactional read-process-write — and explain exactly why that combination gives exactly-once where retries alone can't. Show where the atomic commit boundary sits.
Windows & watermarks on a timeline
Teach me windowing in stream processing: tumbling vs sliding vs session windows, with a one-line "use it when" for each. Then teach watermarks and event-time vs processing-time. Draw an ASCII timeline of events arriving out of order into 5-minute tumbling windows with a 10-minute-late watermark bound. Show one late event that arrives within the bound and gets correctly folded into its (already-emitted?) window, and a second, later event that arrives past the watermark and gets dropped. Make the watermark's position visible at each step so I can see the exact moment a window closes.
Lambda vs Kappa, diagrammed
Draw two Mermaid diagrams: the Lambda architecture (batch layer + speed layer + serving layer) and the Kappa architecture (single streaming path with reprocessing by replay). For each, label where the data flows and where the complexity lives. Then give me a crisp decision rule — a short list of questions I ask about a system that tells me which one to pick — and name the single biggest downside of each. Assume I already have Kafka with generous retention.

Terminology to own

Say these without hesitating

Partition
An ordered, append-only slice of a topic; the unit of parallelism and of ordering.
Offset
A message's position within its partition; consumers commit it to track progress.
Consumer group
A set of consumers sharing a topic's partitions; rebalances when membership changes.
Log compaction
Retention that keeps only the latest value per key, turning a topic into a durable changelog.
Exactly-once
Each event affects the result once despite retries — dedup plus an atomic commit.
Idempotent producer
Sequence-numbered writes so the broker drops retried duplicates.
Tumbling window
Fixed, non-overlapping time buckets; each event lands in exactly one.
Sliding window
Fixed-length windows that overlap; an event can belong to several.
Session window
Dynamic window bounded by a gap of inactivity; length varies per key.
Watermark
A moving "seen everything up to T" bound that decides when to close a window and drop late data.
Event-time vs processing-time
When it happened vs when the engine saw it; window by event-time for correctness.
CDC
Change Data Capture — streaming row-level DB changes, e.g. Debezium reading the transaction log.
Backpressure
A slow consumer propagating its slowdown upstream instead of buffering to OOM.
Kappa vs Lambda
One streaming path (replay to reprocess) vs separate batch + speed layers merged at serving.
Done when
  • You have a running Kafka → Structured Streaming pipeline consuming a keyed event stream.
  • You built a windowed aggregation with a watermark, and can explain what the watermark bounds and why.
  • You demonstrated late-data handling — one late event folded in, one dropped past the bound.
  • You can state your pipeline's delivery semantics precisely, and where at-least-once vs exactly-once holds.
  • You can whiteboard Lambda vs Kappa and defend which one you'd pick for a given system.
