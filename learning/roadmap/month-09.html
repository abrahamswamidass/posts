Core focus

From understanding the model to shipping on top of it

Last month you learned how the model thinks. This month you stop being its student and become its engineer. The job isn't to write clever prompts — it's to wrap a probabilistic core in deterministic scaffolding so the whole system behaves like software you can trust.

Building with the Claude API

Everything starts with the Messages API: a system prompt that sets role, rules, and constraints, then an alternating list of user and assistant turns. Learn the levers cold — temperature (low for extraction and grounded answers, higher for ideation), max_tokens to cap the response, and streaming so a UI feels alive instead of frozen.

  • The engineering mindset — the model is a probabilistic core. Your code is the deterministic scaffolding around it: validation, retries, schemas, guardrails. Treat every model call as an unreliable network dependency that usually gets it right.
  • Prompt caching — mark the stable prefix of a prompt (system prompt, long instructions, a fixed knowledge base) as cached so repeated calls skip re-processing it. This cuts both cost and latency dramatically on anything with a large fixed context.
  • Token budgeting — every request has a finite context window. You are constantly spending tokens across system prompt, retrieved context, conversation history, and the answer. Know roughly what each piece costs and cut what doesn't earn its place.

Prompt engineering that isn't folklore

Most "prompt tips" online are superstition. The real discipline is small and testable.

  • Clear role / task / constraints — state who the model is, exactly what to do, and the hard rules. Ambiguity is where failures breed.
  • Few-shot examples — show two or three worked input→output pairs and the model matches the pattern far better than any adjective-laden instruction.
  • Chain-of-thought — for reasoning tasks, ask it to think step by step before answering; the intermediate reasoning measurably improves the final answer.
  • Structured output — when downstream code has to parse the result, demand JSON against a schema (or use tool-style schemas). Reliable parsing is what turns a demo into a system.
  • Templates & versioning — treat prompts as source code: parameterize them, version them, and test them. A prompt change is a deploy, not a whim.

Why RAG exists

A model has a training cutoff and no access to your private data. Ask it about your company's internal runbook and it will either say it doesn't know or, worse, hallucinate something plausible and wrong. Retrieval-Augmented Generation fixes this by fetching the relevant documents at query time and handing them to the model as context, so the answer is grounded in real source material — with freshness and citations you can point at.

For knowledge-oriented problems, RAG beats fine-tuning almost every time: it's cheaper, updates the instant you change a document, and lets you cite sources. Reach for fine-tuning to change behavior or format, reach for RAG to change what the model knows.

RAG, end-to-end

The whole pipeline is a chain, and every link has its own failure mode:

  • Ingest — pull in the source documents. Failure: garbled extraction from PDFs, lost structure, encoding junk.
  • Chunk — split documents into passages (fixed-size, recursive, or semantic; tune chunk size and overlap). Failure: chunks that split a thought in half or bury the answer across a boundary.
  • Embed — turn each chunk into a vector. Failure: a domain-mismatched embedding model that can't tell your chunks apart.
  • Store — index the vectors in a vector DB (pgvector, Chroma, Pinecone). Failure: wrong distance metric, stale index.
  • Retrieve — pull the top-k most similar chunks for the query. Failure: k too small (misses the answer) or too large (drowns it in noise).
  • Re-rank — optionally reorder retrieved chunks with a stronger model. Failure: skipping it when the top-k is noisy.
  • Assemble context — stitch the best chunks into the prompt within the token budget. Failure: overflow, or the good chunk shoved to the bottom where it's ignored.
  • Generate — prompt Claude with the context and demand a grounded, cited answer. Failure: the model answering from its own memory instead of your context.

Making RAG actually good

Here's the lesson that separates people who've shipped RAG from people who've read about it: retrieval quality is the bottleneck, not the model. If the right chunk never makes it into context, no model on earth answers correctly.

  • Chunking strategy matters most — it's the highest-leverage knob in the whole system. Get chunk size and overlap right for your document type before touching anything else.
  • Hybrid search — combine keyword (BM25) and vector similarity. Vectors catch meaning; keywords catch exact names, codes, and jargon that embeddings blur.
  • Re-ranking — over-retrieve, then use a cross-encoder or a model pass to promote the truly relevant chunks to the top.
  • Grounding & citations — make the model cite the chunk it used. Citations build trust and give you a debugging trail when an answer is wrong.
  • Guard against overflow — enforce the token budget explicitly; drop or summarize before you blow the window.
  • Evaluation — you can't improve what you don't measure. Build a small eval set now; Month 11 turns this into a discipline.
Hands-on challenge
Build · ~10 hours

Build a RAG app over your own content

Nothing teaches RAG like watching it answer questions about documents you wrote. Point it at your own material — your GitHub posts, a stack of PDFs — and make it cite its sources.

  1. Take a document set — e.g. your GitHub posts, or a set of PDFs — and chunk them. Implement two chunking strategies (say fixed-size vs recursive) and compare what each retrieves.
  2. Embed the chunks and store them in pgvector or Chroma.
  3. Implement retrieval — top-k by cosine similarity — and assemble a context window from the results.
  4. Call the Claude API with a system prompt that forces grounded answers with citations back to the specific source chunks.
  5. Handle the "answer not in context" case explicitly: the app says it doesn't know rather than hallucinating.
  6. Ship it as a small web app — FastAPI plus a minimal UI, or Streamlit.
Stretch — Add hybrid keyword+vector retrieval or a re-ranking step, then measure whether answer quality actually improves across 5 fixed test questions. Let the number decide, not your gut.

Prompts that replace the textbook

RAG end-to-end, with the failure modes
You are a staff LLM application engineer mentoring a senior data engineer who is fluent in pipelines and cloud but new to building LLM apps. Explain Retrieval-Augmented Generation end to end. Render the full pipeline — ingest, chunk, embed, store, retrieve, re-rank, assemble context, generate — as a Mermaid flowchart. Then, for each stage, name the single most common failure mode and how you'd detect it. End with the one-sentence reason retrieval quality, not the model, is usually the bottleneck.
Design a chunking strategy
I'm building RAG over [describe my document type — e.g. long technical blog posts / clinical PDFs / API docs]. Compare fixed-size, recursive, and semantic chunking for this specific content. For each, tell me when it wins and when it hurts. Recommend a concrete starting chunk size and overlap for my case and justify the numbers. Then give me a short checklist to tell, by inspecting retrieved chunks, whether my chunking is the thing hurting answer quality.
Harden my grounding system prompt
Here is the system prompt I use for the generation step of my RAG app: [paste prompt]. Rewrite it so that answers are (1) grounded strictly in the provided context, (2) cited back to the specific source chunks, and (3) refuse clearly when the answer isn't in the context instead of guessing. Show the rewritten prompt, then a bullet rationale for each change. Call out any way my current prompt lets the model answer from its own memory.
Generate an evaluation set
Help me build an evaluation set for my RAG app over [describe the corpus]. Generate 10 questions that span easy lookups, multi-chunk synthesis, and at least two questions whose answer is deliberately NOT in the corpus. For each: the question, the expected answer (or "not in context"), what a good grounded+cited response looks like, and what a bad or hallucinated response looks like. Format it as a table I can turn into a test harness.

Terminology to own

Say these without hesitating

RAG
Retrieval-Augmented Generation: fetch relevant documents at query time and feed them to the model as grounding context.
Chunking
Splitting documents into passages sized for embedding and retrieval. The highest-leverage knob in RAG.
Chunk overlap
Shared text between adjacent chunks so an answer straddling a boundary isn't lost.
Embedding
A vector representation of text where semantic similarity becomes geometric closeness.
Vector database
A store indexed for fast nearest-neighbor search over embeddings (pgvector, Chroma, Pinecone).
Top-k retrieval
Returning the k most similar chunks to a query vector as candidate context.
Re-ranking
Reordering retrieved chunks with a stronger model to push the truly relevant ones to the top.
Context window
The finite token budget shared by system prompt, retrieved context, history, and the answer.
Grounding
Constraining the answer to the provided source material rather than the model's memory.
Hallucination
A confident, plausible answer that isn't supported by any real source.
System prompt
The instruction block setting the model's role, rules, and constraints for the whole exchange.
Structured output
Forcing the model to emit JSON against a schema so downstream code can parse it reliably.
Prompt caching
Reusing a processed stable prefix across calls to cut cost and latency.
Done when
  • You have a working RAG app over your own docs that returns answers with citations to the source chunks.
  • It refuses gracefully — says "not in context" — when the answer isn't in the retrieved material.
  • You compared two chunking strategies and can say which retrieved better and why.
  • You can diagram the RAG pipeline end to end and name the failure mode at each stage.
  • You wrote an evaluation set for your app and can measure whether a change helps.
