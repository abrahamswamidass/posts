Production AI Systems & LLMOps

Core focus

The gap between demo and production

A demo proves the model can do the thing once. Production proves it does the thing reliably, at a known cost, without leaking data or hallucinating — and keeps proving it as prompts, models, and data drift underneath you. Everything below is the discipline that closes that gap. You've built the data half of this for ten months; now you make the AI half operable.

Evaluation is the hard part

You can't ship what you can't measure, and "it looked good when I tried it" is not measurement. The foundation is a golden dataset: a curated set of representative inputs paired with expected outputs (or expected properties). You run your system against it and score.

  • LLM-as-judge — use a strong model to grade your system's outputs against an explicit rubric (faithfulness, relevance, correctness) at scale. Powerful, but caveat-laden: judges are biased toward verbose answers, toward their own family of models, and toward the first option shown. Mitigate with a tight rubric, few-shot anchors, position-swapping, and spot-checking judge calls against human labels.
  • Regression testing — freeze the golden set and re-run it on every prompt or model change, so a "small tweak" can't silently degrade quality. This is the unit test of AI engineering.
  • Offline vs online evals — offline runs against the golden set before you ship; online (production) evals sample real traffic and score it live, catching the distribution shift your golden set never anticipated.
  • Task-specific metrics — faithfulness (is the answer grounded in the retrieved context?), relevance (did retrieval pull the right context?), correctness (does it match ground truth?). Pick the two or three that map to your failure modes.

Observability & cost

A production LLM system is a distributed system with a very expensive, non-deterministic hop in the middle. You instrument it accordingly.

  • Tracing — capture every LLM call: inputs, outputs, tokens in/out, latency, retrieved documents, tool calls. LangSmith / Langfuse-style tooling gives you the waterfall so you can see where a slow or wrong answer came from.
  • Token & latency monitoring — dashboards on spend and p50/p95 latency per endpoint, per user, per prompt version. A single unbounded prompt can quietly 10x your bill.
  • The cost levers — prompt caching (reuse the static prefix of a prompt so you don't pay to re-process it), semantic caching (serve a cached answer when a new query is semantically near a previous one), smaller/cheaper models for easy calls, and routing (cheap model first, escalate only when needed).
  • Token budget — treat it as a real engineering constraint, the way you'd treat a latency SLA or a memory ceiling, not an afterthought you discover on the invoice.

Fine-tune vs RAG vs prompt — the decision

The most over-reached-for lever is the one you almost never need. The framework, in order:

  • Prompt engineering first — cheapest, fastest to iterate, no infrastructure. Exhaust it before anything else.
  • RAG for knowledge & freshness — when the model needs facts it doesn't have or that change over time, retrieve them at inference. This is Months 9–10.
  • Fine-tuning for form, style, latency, or a narrow task — when you need a consistent output shape, a specialized tone, or a smaller/faster model that behaves like a bigger one on one job. It changes behavior, not knowledge.

LoRA and other parameter-efficient tuning methods train a small set of adapter weights instead of the full model, cutting the cost and data requirements of fine-tuning by orders of magnitude — but you still need hundreds to thousands of clean labeled examples, a training loop, and an eval harness to prove it helped. Weigh that against RAG, which needs none of it. The honest conclusion most teams reach: prompt + RAG covers the case, and they never fine-tune at all.

Safety, guardrails & responsible AI

The moment an LLM touches a user or a record, it inherits a threat model. Your healthcare lens makes this non-negotiable.

  • Input/output guardrails — validate and filter on the way in (block prompt injection, off-topic, malformed) and on the way out (block PII leakage, unsafe content, ungrounded claims).
  • PII detection & redaction — detect and mask protected data before it reaches the model or the logs. In a healthcare context this is PHI, and it's a compliance requirement, not a nicety.
  • Prompt injection & jailbreaks — treat retrieved documents and user input as untrusted; an attacker can plant instructions in a document your RAG pulls. Separate instructions from data, and never let model output trigger privileged actions without a check.
  • Hallucination mitigation — ground answers in retrieved context, require citations, and let your eval suite fail unfaithful outputs. Grounding plus evaluation is the durable defense; a "please don't hallucinate" instruction is not.
  • Responsible-AI basics — transparency (tell users they're talking to an AI and where answers come from), human oversight on consequential decisions, and a clear boundary on what the system is allowed to do.

LLMOps as the parallel to DataOps/MLOps

None of this is new to you — it's your Month 5 DataOps discipline pointed at a new artifact. Prompts are code: version them. Model choices are config: pin and track them. A prompt change is a pull request, and CI runs your eval suite in the PR — merge only if the golden-set scores hold. Ship behind staged rollouts (canary a small slice of traffic), and monitor for quality drift in production with alerting, the same way you alert on a broken pipeline. LLMOps is DataOps with a stochastic component; the muscles transfer directly.

Hands-on challenge
Capstone · ~15 hours

Capstone II — a production AI system fused with a data pipeline

This is the portfolio piece that proves you're not an AI dabbler bolted onto a data engineer, but someone who ships the whole stack. It must fuse the two halves of this roadmap: a real pipeline feeding a real, evaluated LLM system.

  1. Data pipeline (Months 1–6) — ingest and prepare a knowledge source into your lakehouse / vector store on a schedule. Orchestrated, incremental, quality-checked. This is the fuel, and it must run on its own.
  2. LLM layer (Months 9–10) — serve a RAG or agent over that knowledge through an API. Clean request/response contract, versioned prompts.
  3. Eval suite — build a golden dataset (inputs + expected outputs) and an LLM-as-judge rubric, and wire it to run as a regression test. A change that drops your scores should fail the build.
  4. Observability — trace every call and log tokens, latency, and cost to a small dashboard. You should be able to answer "what did this cost and how slow was it" at a glance.
  5. Guardrails — PII redaction on inputs and logs, and grounded, cited answers on outputs. Show a refusal path when the context can't support an answer.
  6. Professional README — an architecture diagram (Mermaid), the eval results, a cost/latency table, and a written fine-tune-vs-RAG rationale explaining why you chose what you chose.

Publish it as a public GitHub repo — portfolio piece #2, and the one hiring managers will actually read.

Stretch — add semantic caching and show the cost/latency improvement in real numbers (before/after tokens, dollars, and p95) in the README.
Learn it with Claude

Prompts that replace the textbook

Paste these into Claude one at a time. Push back, ask for diagrams, ask "why not the other way." Conversation beats reading.

Build the eval harness
You are a staff AI engineer who has shipped evaluated LLM systems. Help me build an evaluation setup for my RAG/agent. Walk me through: (1) how to construct a golden dataset of inputs and expected outputs from my domain, including how many examples and how to cover edge cases; (2) design an LLM-as-judge prompt that scores faithfulness, relevance, and correctness against a rubric, with a numeric scale and few-shot anchors; (3) enumerate the failure modes of LLM-as-judge (verbosity bias, position bias, self-preference) and give me a concrete mitigation for each. Give me the judge prompt as copy-pastable text.
The fine-tune vs RAG vs prompt decision
Create a decision-framework document for choosing between fine-tuning, RAG, and prompt engineering for a specific use case (I'll describe mine: a healthcare knowledge assistant over changing clinical documents). For each option lay out the cost, engineering effort, data requirements, latency impact, and the failure it fixes vs the failure it doesn't. Give me a decision tree I can follow in under two minutes, and end with a one-paragraph recommendation for my case with the reasoning stated explicitly. Add a short note on where LoRA fits.
Guardrails for healthcare data
Design a guardrails and PII/PHI redaction strategy for an LLM system that touches healthcare data. Enumerate the risks in a table — prompt injection, PHI leakage into prompts and logs, hallucinated clinical claims, unsafe content, over-broad actions — and for each give the specific control (input filter, output filter, redaction step, grounding requirement, human-in-the-loop). Then draw a Mermaid diagram of where each guardrail sits in the request/response flow. Flag anything that has HIPAA implications I should not get wrong.
Review my capstone as a skeptic
Act as a staff AI engineer reviewing my Capstone II architecture and evaluation approach. Here is my design: [paste architecture + eval plan]. Be adversarial. List the 5 weakest points — where it will break under real traffic, where the eval is measuring the wrong thing, where cost or latency will surprise me, where a guardrail is missing. For each, tell me the sharper way to do it and roughly how much work the fix is. Don't be reassuring; assume this is going in front of a hiring committee.
Mock interview — production AI engineer
Act as a hiring manager screening me for an LLMOps / production AI engineer role. Ask me 6 questions ONE at a time, covering evaluation, observability, cost control, safety/guardrails, and the fine-tune-vs-RAG decision. Wait for my answer to each. After each, rate it 1–5, correct anything wrong, and give me the crisper senior-level phrasing. At the end give an overall readiness score and the one topic I should drill before Month 12.
Terminology to own

Say these without hesitating

Eval
A repeatable measurement of system quality against known inputs. The core discipline of AI engineering.
LLM-as-judge
Using a model to grade outputs against a rubric at scale. Powerful but bias-prone; anchor and spot-check it.
Golden dataset
Curated inputs paired with expected outputs/properties, used to score and regression-test a system.
Regression testing
Re-running the golden set on every change so quality can't silently degrade.
Tracing
Capturing inputs, outputs, tokens, and latency for every LLM call to debug and monitor.
Token budget
A hard cost/latency constraint on tokens per call, treated like an SLA.
Prompt caching
Reusing the processed static prefix of a prompt to avoid paying to recompute it.
Semantic caching
Serving a cached answer when a new query is semantically close to a prior one.
Fine-tuning
Training a model on examples to change form/style/latency — not to add knowledge.
LoRA
Parameter-efficient fine-tuning that trains small adapter weights instead of the full model.
Guardrail
An input/output check that blocks unsafe, off-topic, ungrounded, or PII-bearing content.
Prompt injection
Malicious instructions planted in user input or retrieved documents to hijack the model.
LLMOps
DataOps/MLOps for LLM systems: versioned prompts, evals in CI, staged rollout, drift monitoring.
Done when
  • You have a public Capstone II repo that fuses a data pipeline with an LLM system, both running end to end.
  • You built an eval suite — golden set plus an LLM-as-judge rubric — that runs as a regression test on every change.
  • You have tracing in place with tokens, latency, and cost logged to a dashboard.
  • Your system redacts PII and returns grounded, cited answers with a refusal path.
  • You wrote a fine-tune-vs-RAG rationale and can defend the choice out loud.
