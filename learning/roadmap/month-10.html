Agents, Tool Use & the Model Context Protocol

Core focus

A model that acts, not just answers

For nine months you've built systems that produce output — a query, a mart, a summary, a retrieved answer. An agent is different in kind: it's an LLM placed in a loop with tools and a goal, allowed to take actions in the world and read the consequences. That's a powerful primitive and a dangerous one, and this month is about wielding both halves.

From chatbot to agent

An agent is an LLM in a loop: it looks at a goal, decides which tool to call, reads the result, and iterates until it's done. Contrast the three shapes you'll now be able to name precisely:

  • Prompt — one call in, one answer out. No tools, no state. Most tasks are this and should stay this.
  • Chain — a fixed, pre-authored sequence of calls (summarize → classify → format). You decide the control flow; the model just fills each step.
  • Agent — the model decides the control flow at runtime: which tool, in what order, when to stop. Non-deterministic by design.

The senior instinct here is restraint. An agent buys you flexibility on open-ended, multi-step tasks — and pays for it with latency, cost, non-determinism, and new failure modes. If you can express the work as a chain, do that. Reach for an agent only when the path genuinely can't be known ahead of time. Often you don't need one.

Tool / function calling

This is the core mechanic underneath every agent. You describe each tool with a JSON schema — a name, a natural-language description, and typed parameters. You pass those definitions to the model. When the model decides a tool is needed, it doesn't run anything; it returns a structured request to call one, with arguments. Your code executes the call, and you feed the result back into the conversation so the model can continue.

  • The model never touches your database or your shell — it only emits an intent. Execution stays entirely in your code, which is exactly where your guardrails live.
  • The description field is prompt engineering, not documentation. It's how the model decides when to reach for the tool and how to fill the arguments. Vague descriptions produce wrong or hallucinated calls.
  • Keep schemas tight: required vs optional parameters, enums instead of free text where you can, and one clear job per tool. A bloated tool with ten modes is a bloated decision for the model.

The ReAct loop & planning

The pattern that ties it together is ReAct: reason → act → observe → repeat. The model reasons about what to do, acts by requesting a tool, observes the returned result, and loops — until it has enough to give a grounded final answer. Around that core you'll see:

  • Planner / executor — one step (or one agent) decomposes a multi-step task into a plan; another carries out each step. Useful when the task is big enough that "figure it out as you go" wanders.
  • Memory — short-term memory is just the context window (the running transcript). Longer-term memory is an external store (a vector index, a scratchpad, a database) the agent reads from and writes to across turns or sessions.
  • Where loops go wrong — infinite loops (the model never decides it's done), calling the wrong tool, and hallucinated arguments (inventing a table name or an ID). Every one of these is why you cap iterations and validate arguments rather than trust them.

The Model Context Protocol (MCP)

MCP is the open standard for connecting models to tools and data. Instead of hand-writing a bespoke integration for every tool in every app, you run an MCP server that exposes tools, resources, and prompts over a defined protocol, and any MCP client (a host app, an IDE, Claude itself) can connect to it. Think of it as a universal adapter — the USB-C of model integrations — rather than a drawer of proprietary cables.

  • How it relates to tool use — MCP doesn't replace function calling; it standardizes the plumbing around it. The model still emits a structured tool request; MCP defines how that tool was discovered, described, and invoked across a client/server boundary and transport.
  • Why it matters — write your "query the warehouse" tool once as an MCP server and every MCP-aware client can use it, no per-app glue. The ecosystem of servers (databases, filesystems, SaaS APIs) is growing fast, and it ties directly to Claude, which speaks MCP natively.

Safety: guardrails & human-in-the-loop

An agent with real tools near real data is a production system, not a toy — and this is the part demos skip. Guardrails are the difference between a slick demo and something you'd point at a healthcare database. The layers you build:

  • Input / output validation — sanitize what goes in, schema-check what comes back, and never execute an argument you haven't inspected.
  • Allow-lists & least privilege — the agent gets a small, explicit set of tools, and each tool is scoped down (read-only DB user, specific tables, row limits) so the blast radius is bounded even if the model goes wrong.
  • Sandboxing & limits — run tools in a constrained environment, and cap loop iterations and spend so a runaway agent stops itself.
  • Human-in-the-loop — for any high-stakes or irreversible action (a write, a delete, an email, a payment), the agent proposes and a human approves. In your world, near PHI, that gate is non-negotiable.
Hands-on challenge
Build · ~10 hours

Build a tool-using data-analyst agent

Wire the Claude API into a real agent loop with tools, then harden it until you'd trust it near production data. Use your existing infrastructure — this isn't a greenfield toy.

  1. Build a data-analyst agent with the Claude API that has tools. At minimum a query_warehouse tool (text-to-SQL against your Month-6 lakehouse or a local Postgres) and one more — a calculator, or a search over your Month-9 RAG index.
  2. Implement the tool-calling loop: the model requests a tool, you execute it, you return the result, and it continues — iterating until it produces a grounded final answer, not a guess.
  3. Add guardrails: validate and constrain the SQL (read-only connection, enforced row limits, reject anything that isn't a SELECT), cap the number of loop iterations, and reject unsafe or out-of-scope requests.
  4. Add a human-in-the-loop confirmation for any write action — the agent must propose and wait for explicit approval before anything mutates.
  5. Test it on 5 real analytical questions and log the full tool-call traces — every request, argument, and result — so you can see exactly how it reasoned.
Stretch — Expose one of your tools as an MCP server and connect to it from an MCP client, OR add a second agent — a critic — that checks the first agent's answer against the data before it's returned.
Learn it with Claude

Prompts that replace the textbook

Paste these into Claude one at a time. Push back, ask for diagrams, ask "why not the other way." Conversation beats reading.

Prompt vs chain vs agent
You are a staff AI engineer mentoring a senior data engineer who is fluent in distributed systems and SQL but new to agentic AI. Explain the difference between a single prompt, a fixed chain, and an agent — where control flow lives in each, and what non-determinism buys and costs you. Draw a Mermaid diagram of the ReAct loop (reason → act → observe → repeat) with a tool call and its result. End with a crisp rule of thumb for deciding when an agent is actually worth it versus when a plain chain is the right call.
Design a text-to-SQL tool schema
Help me design a clean tool schema for a text-to-SQL tool that an agent will call to query a data warehouse. Give me the full JSON tool definition (name, description, parameters with types and which are required). Focus especially on writing the description field so the model uses the tool correctly — when to call it, how to phrase the SQL, and what constraints apply (read-only, row limits). Then show me 2 examples of a good structured tool-call request the model would emit, and 2 bad ones, and explain what makes the bad ones fail.
MCP architecture, explained
Explain the Model Context Protocol to me as an engineer. Cover the architecture — MCP servers, clients/hosts, and the transport between them — and what a server actually exposes (tools, resources, prompts). Render a Mermaid diagram of a client connecting to one or more MCP servers. Then explain precisely how MCP differs from raw function calling: what problem it solves that plain tool definitions don't, and why "write the tool once, use it from any client" matters. Use Claude's native MCP support as the concrete example.
Guardrails for a healthcare agent
Design guardrails for an agent that can query a healthcare database containing PHI. Enumerate the risks — think prompt injection, over-broad queries, hallucinated arguments, data exfiltration, runaway loops, unauthorized writes — and for each risk give the concrete control that mitigates it (allow-lists, read-only scope, row limits, output validation, iteration caps, human-in-the-loop approval, audit logging). Present it as a table: risk, how it manifests, control. End with the three controls you'd never ship without.
Mock interview — AI/agent engineer
Act as a hiring manager screening me for an AI/agent engineer role. Ask me 6 questions one at a time — covering tool/function calling, the ReAct loop, MCP, guardrails, and agent failure modes — and wait for my answer to each before moving on. After each answer, rate it 1–5, correct anything wrong, and give me the sharper way to say it. At the end, give me an overall readiness score and the one concept I should drill before Month 11.
Terminology to own

Say these without hesitating

Agent
An LLM in a loop with tools and a goal, deciding its own actions until done.
Tool / function calling
The model emits a structured request to call a tool; your code executes it and returns the result.
Tool schema
The JSON definition — name, description, typed parameters — that tells the model how and when to use a tool.
ReAct loop
Reason → act → observe → repeat, until the model has enough to answer.
Planner / executor
Split a task: one step decomposes it into a plan, another carries out each step.
Memory
Short-term = the context window; long-term = an external store the agent reads and writes.
Model Context Protocol (MCP)
Open standard for connecting models to tools and data — a universal adapter.
MCP server
A process that exposes tools, resources, and prompts to any MCP client over the protocol.
Multi-agent orchestration
Multiple agents (e.g. worker + critic) coordinating to complete a task.
Guardrail
A control — allow-list, validation, limit, sandbox — that bounds what an agent can do.
Human-in-the-loop
A human approval gate before any high-stakes or irreversible action runs.
Text-to-SQL
Turning a natural-language question into a SQL query the agent can execute.
Done when
  • You have a working tool-using agent with a query tool and a real reason→act→observe loop.
  • Your guardrails limit tool actions (read-only, row caps) and cap the loop count.
  • A human-in-the-loop gate blocks any write until you approve it.
  • You can diagram the ReAct loop from memory and explain what MCP adds over raw function calling.
  • You logged and reviewed real tool-call traces from 5 analytical questions.
