Orchestration, DataOps & Data Quality

Pipelines that run aren't the same as pipelines you can trust. This month is about the discipline that separates a script kiddie from a platform engineer — orchestration, data contracts, quality gates, lineage, and CI/CD for data.

Core focus

From "it ran" to "I trust it"

You already run Airflow at Cardinal. So this month isn't about wiring a DAG — it's about the reliability engineering that sits on top of one. The gap between a data engineer and a platform engineer is entirely here: contracts, gates, lineage, and the CI/CD that lets you change a pipeline without holding your breath. Every term below is something a healthcare data platform lives or dies on.

Orchestration, past the basics

You know how to author a DAG. The seniority signal is speaking to Airflow's internals and its failure modes without hand-waving:

  • Operators vs sensors — operators do a unit of work; sensors wait for a condition (a file lands, a partition appears). Know why a naïve sensor pins a worker slot and why reschedule mode and deferrable/async sensors exist.
  • XComs — the cross-task message bus for small values (an id, a path, a row count). Know the trap: XComs are for pointers, not payloads — push a GCS URI, not a DataFrame.
  • Idempotent tasks + safe retries — a task that reruns must land the same state. This is what makes automatic retries and backfills safe instead of a duplicate-data incident waiting to happen.
  • Backfills & catchup — running historical intervals on demand. Know catchup=True/False, why a scheduler-triggered catchup storm has taken down more than one team, and how partition-scoped writes keep a backfill from double-counting.
  • Dynamic task mapping — fan out N tasks at runtime from a list you don't know until the DAG runs (.expand()), instead of hand-coding tasks or abusing the DAG-parsing loop.
  • Dependencies & SLAs — task ordering, trigger rules (all_success, one_failed), and per-task SLAs that alert when a step blows its time budget.

Where Airflow strains: it orchestrates tasks, not data. It has no native notion of "this table is stale" or "this asset depends on that asset." Local development is heavy, testing is awkward, and backfills bolt onto a scheduler that was really built for wall-clock schedules. Those pain points are exactly what the next tools attack.

The asset-based shift (Dagster / Prefect)

The industry is moving from task-centric to data-centric orchestration. Airflow asks "run these tasks in this order." Dagster asks "here are the software-defined assets (tables, models, files) I want to exist, and how each is computed" — then works out the execution graph, tracks freshness, and knows what to rematerialize when an upstream asset changes.

  • Dagster — assets as first-class objects, typed IO, built-in lineage, a real local dev loop, and native awareness of freshness and partitions. The strongest fit when the pipeline is a graph of tables.
  • Prefect — lighter, Pythonic, flow/task decorators with dynamic runtime graphs; shines for glue and irregular workflows more than a warehouse asset graph.
  • When to reach for which — stay on Airflow for broad ecosystem, existing ops, and heterogeneous task orchestration; reach for Dagster when you want data-aware materialization, testability, and lineage out of the box; reach for Prefect for lightweight dynamic Python workflows. You don't have to migrate to speak this fluently — but you must be able to argue the trade-off in a design review.

Data quality gates

You test code. Untested data is the last big blind spot on most teams. The fix is to assert on data the same way you assert on functions — and to fail the pipeline when the assertion breaks, so bad rows never reach gold.

  • Great Expectations — declare expectations ("patient_id is never null", "row_count between 10k and 2M"), group them into a suite, and run a checkpoint as a task in the DAG. A failing checkpoint stops the run.
  • dbt tests — the built-ins cover most of it: unique, not_null, relationships (referential integrity), accepted_values. Add custom singular/generic tests and dbt-expectations for distribution and volume checks.
  • Quality gate / circuit breaker — the gate sits between silver and gold: transform, then test, then only publish on green. A red test trips the breaker and the bad batch is quarantined, not promoted.
  • Anomaly detection — beyond hard rules, watch for drift in volume (row counts out of band), freshness (arrived late), and distribution (a column's mean/null-rate shifts). These catch the failures no static rule anticipated.

Data contracts & schema enforcement

A data contract is an explicit, versioned agreement between the producer of a dataset and its consumers, covering schema (columns, types, nullability), semantics (what a field means), and SLAs (freshness, availability). Enforce it at the boundary — reject or quarantine data that violates the contract before it enters your pipeline, and treat a breaking schema change as a versioned, negotiated event, not a surprise.

This is the cure for the classic incident: an upstream team renames dob to birth_date or flips a type, and every downstream model silently breaks or, worse, produces wrong numbers. With a contract, that change fails CI on the producer's side before it ever ships. In a PII/healthcare context the contract also pins which fields are sensitive and how they may be used.

Observability, lineage & CI/CD

The five pillars of data observability — the checklist for knowing your data is healthy: freshness (is it recent?), volume (is the row count right?), schema (did the structure change?), distribution (are the values in expected ranges?), and lineage (where did it come from, what breaks if it changes?).

  • Lineage & OpenLineage — a map of how datasets derive from one another. OpenLineage is the open standard for emitting it, including column-level lineage so you can answer "if this source column dies, exactly which gold metrics go dark?"
  • Freshness SLAs / SLOs — a stated promise ("orders_gold is never more than 2 hours stale") with monitoring and alerting when it's missed. This is your on-call contract with the business.
  • CI/CD for data — treat pipeline and dbt changes like application code: run tests on the PR, build against a staging environment or a slim/CI dataset, review the plan, and deploy on merge. No more editing transforms straight in prod.

The umbrella over all of it is DataOps — applying DevOps discipline (automation, testing, version control, monitoring, fast feedback) to the data lifecycle. Orchestration, contracts, gates, lineage, and CI/CD aren't five separate topics; they're the five limbs of one practice.

Hands-on challenge
Build · ~8 hours

Make the pipelines from Months 2–3 trustworthy

You already have transforms. This challenge wraps them in the reliability layer — the difference between code that runs on your laptop and a platform someone can page you about.

  1. Orchestrate end-to-end. Wire your dbt + Spark jobs into a single graph in Airflow (Astro CLI, local) or Dagster — extract/land, Spark transform, dbt build, in the right dependency order.
  2. Prove idempotency. Make one task idempotent (delete-insert by partition, or a merge on key) and demonstrate that running it twice leaves the row count identical — no duplicates.
  3. Add a quality gate that fails the run. Add Great Expectations (or dbt tests) asserting not_null, uniqueness, and a row-count range. Then inject bad data and watch the checkpoint stop the pipeline before gold.
  4. Wire a freshness check. Add a freshness assertion with an explicit SLA ("silver must be < 1 hour old") and make a stale run alert or fail.
  5. Capture lineage. Generate a lineage graph — dbt docs graph or an OpenLineage emitter — and screenshot the DAG of tables so you can point at exactly what feeds what.
  6. Add a CI check. Set up a minimal CI workflow (GitHub Actions) that runs your dbt tests on a pull request, so a bad change fails before merge.
Stretch — Write a one-page data contract for one source table: schema (columns/types/nullability), semantics (what each field means), owner, freshness SLA, and a breaking-change policy. Make it the kind of doc you'd actually send to an upstream team.

Prompts that replace the textbook

Paste these into Claude one at a time. Push back, ask for diagrams, ask "why not the other way." Conversation beats reading.

Idempotency & safe backfills
You are a staff data platform engineer mentoring a senior software engineer who already runs Airflow in production but wants to sharpen the reliability side. Explain what makes an Airflow task idempotent and why it's the precondition for safe retries and backfills. Walk through a concrete delete-insert-by-partition example: show the SQL/logic for a task that, when rerun for the same logical date, produces identical output with no duplicates. Then explain catchup and backfill behavior, the catchup-storm failure mode, and three techniques to keep a backfill from double-counting. End with the two sentences I'd use to explain idempotency to a skeptical teammate.
Task-based vs asset-based orchestration
Contrast task-based orchestration (Airflow) with asset-based / software-defined-asset orchestration (Dagster). Explain what changes conceptually when the unit of orchestration becomes the data asset instead of the task, and why the industry is trending this way. Render a Mermaid diagram showing the same pipeline modeled both ways — an Airflow task DAG and a Dagster asset graph — side by side. Finish with a crisp decision rule: given a new project, when do I stay on Airflow, when do I reach for Dagster, and when for Prefect?
Design a data-quality gate
Teach me to design a data-quality gate with Great Expectations. Explain expectations, suites, and checkpoints, and exactly where the checkpoint task sits in a DAG relative to the transform and the publish-to-gold step. Give me a worked example: a suite that asserts patient_id is never null, a uniqueness rule, and a row-count-between range. Show what happens — step by step — when I inject bad data and the checkpoint fails, and how that trips a circuit breaker so nothing reaches gold. Draw the DAG with the gate in place as a Mermaid flowchart.
Contracts & the five pillars
Explain data contracts (producer/consumer agreement on schema, semantics, and SLAs, enforced at the boundary) and the five pillars of data observability (freshness, volume, schema, distribution, lineage). Use a healthcare example: an upstream team renames a patient demographics column. Walk through, with and without a contract, how the incident plays out — and show how the contract catches the breaking change in CI before it ships. Then give me a one-line definition of each of the five pillars as I'd say them in a review.

Terminology to own

Say these without hesitating

Idempotency
Re-running a task yields identical state — no duplicates, no drift. The precondition for safe retries and backfills.
Backfill
Running a pipeline over historical intervals on demand; safe only when tasks are partition-scoped and idempotent.
Sensor
An Airflow task that waits for a condition (a file, a partition) rather than doing work; use reschedule/deferrable mode to free the worker.
XCom
Airflow's cross-task message bus for small values (ids, paths). Pass pointers, not payloads.
Software-defined asset
A declared data object (table/file) and how it's computed; the unit of asset-based orchestration in Dagster.
Data contract
A versioned producer/consumer agreement on schema, semantics, and SLAs, enforced at the boundary.
Data lineage
The dependency map of how datasets derive from one another; column-level via OpenLineage.
Freshness SLA / SLO
A stated, monitored promise about how recent a dataset must be, with alerting when missed.
Circuit breaker
A gate that halts the pipeline on a failed check so bad data is quarantined, not promoted.
Quality gate
A test step between silver and gold that only publishes on green.
Observability (5 pillars)
Freshness, volume, schema, distribution, lineage — the checklist for knowing data is healthy.
DataOps
DevOps discipline applied to the data lifecycle: automation, testing, version control, monitoring, fast feedback.
Done when
  • You've orchestrated a dbt + Spark pipeline end-to-end in Airflow or Dagster.
  • You built a quality gate that stops the run when you inject bad data.
  • You proved one task is idempotent — a re-run leaves the row count unchanged.
  • You captured lineage and wired a freshness check with an explicit SLA.
  • You wrote a one-page data contract for a source table.
